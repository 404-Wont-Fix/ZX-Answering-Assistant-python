## 序：能点起来的时候，真的挺高兴

这个项目最开始用的是浏览器自动化。

对当时的我来说，这条路比较好理解：人能打开页面、找到题目、选择选项、点提交，那能不能让程序照着做？比起一上来就研究接口和签名，“让浏览器帮我点一下”至少看得见，也容易知道程序走到了哪一步。

先让它动起来，再一点点补功能。对基础有限的人来说，能走通一段流程，本来就是一件很有成就感的事。

但能跑一次，和能一直跑，是两回事。

早期浏览器方案的准确性和稳定性一直不太理想。自动化脚本眼里的页面，是选择器、元素、文本和等待条件；人看起来差不多的页面，在程序看来不一定还是同一个东西。页面没准备好、选项没匹配好、提交状态没判断清楚，都可能把后面的流程带偏。

我不是突然觉得浏览器自动化“不高级”才换思路，而是被这些实际问题推着，开始想另一件事：

**页面上点完按钮之后，它到底给服务器发了什么？**

这个问题，才是后来折腾 API 的起点。

## 第一章：先别猜，让网页自己演示一遍

网站不是靠按钮本身完成业务的。按钮背后的 JavaScript 会整理参数、发起请求，服务器返回结果，页面再决定显示什么。

以前我盯着“程序点没点到按钮”，现在开始看“点了按钮之后发生了哪个请求”。视角只挪了一点，看到的东西就完全不同了。

### 把一次操作拆小

整理下来，一个适合基础有限的人跟着做的分析顺序是：

1. 用有权限的账号正常登录，打开浏览器开发者工具。
2. 在 **Network（网络）** 中筛选 Fetch/XHR，必要时开启 Preserve log 保留跳转前后的记录。
3. 不要一口气点完所有流程。分别观察打开课程、开始一个知识点评估、保存一题和最终提交时的请求。
4. 对每个请求记录 URL、方法、查询参数、请求体、认证头，以及响应 JSON。
5. 将请求与页面动作对应起来。看到一个名字像“提交”的接口，先不要认定它就是全部流程。

```text
一次正常页面操作
  ↓
Network 找到新增的请求
  ↓
Headers / Payload：网页送了什么？
  ↓
Response：服务器回了什么？
  ↓
Initiator / Sources：是哪段 JS 组织了它？
  ↓
整理字段来源与调用顺序
  ↓
本地复现数据处理，再在授权范围核对最小流程
```

Network 里会有不少与评估无关的请求。先围绕一次动作找关联，比一上来试图看懂整个网站要现实得多。

### 我需要的不是一长串 URL，而是一条链

当前学生评估引擎的基础地址是：

```text
https://ai.cqzuxia.com/evaluation/api
```

以下路径按 [`src/answering/api_answer.py`](../src/answering/api_answer.py) 保留原有大小写，不能据此推断服务端一定忽略大小写：

| 页面/业务动作 | 方法与相对路径 | 关键数据 |
| --- | --- | --- |
| 获取课程列表 | GET `/StudentEvaluate/GetCourseList` | 引擎提供的课程列表方法；GUI 也使用认证模块中的课程查询能力 |
| 查看知识点状态 | GET `/studentevaluate/GetCourseInfoByCourseId` | `CourseID`；响应中检查 `testMemberInfo.isPass/times` |
| 找未完成章节 | GET `/StuEvaluateReport/GetUnCompleteChapterList` | `CourseID`；章节下的 `knowledgeList` |
| 开始知识点评估 | GET `/studentevaluate/beginevaluate` | `kpid`、`sign`；取得 `questionList` |
| 保存一道题 | POST `/StudentEvaluate/SaveEvaluateAnswer` | `kpid`、`questions`、`sign` |
| 提交评估信息 | POST `/StudentEvaluate/SaveTestMemberInfo` | `kpid`、空 `questions`、`sign` |

学生登录的 `/connect/token` 不属于上面这个 `/evaluation/api` 路径前缀。项目在浏览器登录时监听它的响应，拿到 `access_token`，后续请求使用 Bearer token。

先把这几个概念分开，后面就没那么绕：

- `CourseID`：正在处理哪门课程。
- `kpid`：正在处理哪个知识点，不是题目 ID。
- 题目 ID：本次题目在题库里对应哪条记录。
- 选项 ID：提交哪个选项，不是页面上的 A/B/C 字母。
- `access_token`：当前登录身份。
- `sign`：按规则算出的请求校验值。

接口名只能提供线索，不能代替分析。尤其是“保存一题”和“交卷”，名字都带 Save，作用却不是一回事。

## 第二章：参数大多看得懂，偏偏多了个 sign

课程、知识点、题目、答案，这些字段至少能和页面上的东西对上。

`sign` 不一样。它不是我手动输入的，也不是题目选项里直接给出来的，却会跟着请求一起出现。

这部分不是一路顺着查就成功了。中间我确实放弃过一次，原因现在说出来甚至有点简单：名字明明摆在那里，我却只认出了自己认识的那半截。

### 第一次：看见了 SHA256，却没看懂前面的 HMAC

当时我在网页 JS 里找到了一处方法或函数调用，具体叫什么已经记不清了，只记得相关代码里有 **HMAC-SHA256** 字样，还硬编码了一个 key。

问题是，我当时只认识 SHA256。

于是就按自己理解的 SHA256 去处理，结果算出来的内容和开发者工具抓到的签名不一致。那个写在代码里的 key 我也看到了，但不知道它到底是干什么用的，更没把它和算法名称前面的 HMAC 联系起来。

现在回头看，线索其实已经在眼前了。可对当时的我来说，看到一段代码和理解它，完全是两回事。

算不一致，又不知道问题在哪儿，这条路就暂时搁下了。项目继续使用浏览器自动化，至少那条路还能往前走。

并不是所有卡住的问题，都会在当晚迎来一个漂亮的解决方案。有时候就是先放下，继续用手里能用的东西。

### 第二次：越想越不对，会不会算法就弄错了？

后来有一次，我越想越觉得不对，又重新打开网页 JS 看了一遍。

这次开始怀疑的不是“是不是少复制了某个参数”，而是更前面的一步：**会不会我从一开始就用错了算法？**

于是把完整的 **HMAC-SHA256** 拿去搜索，不再只盯着自己认识的 SHA256。看到它的含义之后，之前那个不知道干什么用的 key，终于有了位置。

原来不是对一段内容直接算 SHA256，而是要把 **key 和内容一起交给 HMAC-SHA256**。

用现在能理解的方式写出来，两者的区别是：

```text
之前理解成：SHA256(内容)
实际使用的是：HMAC-SHA256(key, 内容)
```

HMAC 使用 SHA256 作为内部哈希算法，但不等于普通 SHA256，也不等于随手把 key 拼到内容前面再算一次。这里的 key 是 HMAC 的密钥参数，不是一个可有可无的附加字段。

那个 key 并不是这一次才找到的。它上次就在那里，只是这次我终于明白该把它放在哪儿。

### 算法找对了，还得知道它到底吃了什么

有了上一次的经验，我重新打断点，一点点跟着 JS 往下走。这次目标很具体：找到签名函数被调用之前，传给它的那份信息。

最后跟到了保存这份信息的变量，成功看到了它的原始值。

这一步特别重要。Network 能让我看到请求最终带出去的签名，但它不会直接告诉我，网页在签名前究竟把哪些字段拼成了什么样子。到了断点这里，我才不用再对着请求体猜原文。

接下来，把这次看到的原始值、网页里硬编码的 key，以及重新确认的 HMAC-SHA256 算法放到一起计算，再拿结果和开发者工具抓包里的签名作对比。

**两边完全一致。**

不是“长得有点像”，也不是“位数一样”，而是本次样本的计算结果与请求中的签名对上了。折腾到这里，这条签名生成链路才算真正弄明白。

```text
第一次读 JS
  ├─ 看见 HMAC-SHA256，却只按 SHA256 理解
  └─ 看见硬编码 key，却不知道它的用途
       ↓
计算结果与抓包签名不一致 → 暂时放弃，继续浏览器自动化
       ↓
后来重新读 JS，怀疑算法用错
       ↓
搜索完整名称 HMAC-SHA256 → 明白 key 的作用
       ↓
重新打断点，逐步追到签名函数接收的原始变量
       ↓
原始值 + 硬编码 key → HMAC-SHA256 → 本地计算结果
                                             │
抓包中同一次请求的 sign ──────────────────── 对比
                                             ↓
                                         完全一致
                                             ↓
整理分析结果，交给 AI 完成 API 模式开发
```

这里的“一致”是对当时验证样本的回顾，不是承诺网站以后改了也永远有效。具体函数名、变量名已经记不清，就不为了让故事显得专业再补一个。

### 最后才是：把弄明白的东西交给 AI 实现

签名链路分析和对比完成之后，我把这些信息整理好发给 AI，让它完成这个 API 模式的开发。

这段经历里，AI 的作用不是凭空猜出网站协议，更不是一句“帮我做个答题功能”就自动把问题解决了。关键是我先弄清了算法、key、输入原文和抓包结果的对应关系，再把验证过的信息交给它实现。

编程基础有限，确实会在把完整流程写成代码时需要很多帮助。但断点里那个变量是什么、换成正确算法后能不能和抓包结果对上，这些判断仍然得有依据。

这也成了我后来觉得比较有用的协作方式：**自己观察、追踪和验证，把能确认的事实整理清楚，再让 AI 帮忙落地成代码。**

### 留给以后维护时的找路方法

上面是这次真实经历。下面是整理后的辅助方法，不表示我当时逐项用了所有功能：

1. 从 Network 的 **Initiator（发起程序）** 查看请求调用来源，或者在 **Sources（源代码）** 搜索接口名。
2. 压缩文件挤成一行时，用 `{}` 格式化，先看清函数边界；格式化不等于反混淆，也不要求一定存在 source map。
3. 从 `sign` 的赋值沿调用关系追到生成函数，确认完整算法名称和 key 的来源，不凭熟悉的半个名字下结论。
4. 在调用前打断点，逐步执行，观察输入变量的真实值，而不是根据最终请求体猜测签名原文。
5. 对同一份样本比较本地结果与请求里的签名。对不上时，分别检查算法、key、原文和输出格式。
6. 将已经验证的内容与仍不确定的地方分开记录，再交给 AI 协助实现或排查。

## 第三章：把走通的签名过程拆开看

有了上面那次对比，才有了后面的实现。下面不再按当时的试错顺序讲，而是对照当前源码，把已经整理好的规则拆开。

当前实现用的是 **HMAC-SHA256**，输出小写十六进制字符串。

不是参考项目里的 MD5 加盐，也不是“对整个请求体随便算一个 SHA256”。不同网站的故事可以参考，算法不能照抄。

用概念式表示：

```text
sign = HMAC-SHA256(key 的 UTF-8 字节, 签名原文的 UTF-8 字节)
       → 小写十六进制
```

`APIAutoAnswer.generate_sign()` 做的就是这一步。当前代码使用固定 `SIGN_KEY`；本文不再复制实际常量，示例全部用 `demo-key-not-for-production`，避免文档与源码各维护一份值。

HMAC 不是把内容加密后发出去：请求数据仍可读。也不要把这里的前端签名机制描述成账号授权机制——登录是否有效、能操作哪个课程，仍要由服务端验证。

### 真正要一字不差的，是签名原文

对人来说，这两段 JSON 是同一个意思：

```json
{"questionid":"q-demo","answerid":"a-demo"}
```

```json
{"questionid": "q-demo", "answerid": "a-demo"}
```

但它们不是同一串字节。第二段多了空格，如果直接送去计算 HMAC，结果就不同。

这也解释了为什么“参数看起来都一样”不是一个足够精确的判断。签名函数不理解“意思差不多”，它只处理输入字节。

### 第一关：开始评估

`_begin_evaluate_request()` 构造的原文是：

```text
kpid=kp-demo
```

先对这个**未做 URL 编码**的字符串签名，再把 `kpid` 和 `sign` 用 `urlencode` 放入 GET 查询参数。

```text
原始 kpid → "kpid=" + kpid → 签名
                               ↓
                    kpid 与 sign 一起 URL 编码
                               ↓
                         GET beginevaluate
```

“请求 URL 需要编码”不等于“签名输入也先编码”。这个先后顺序不能凭习惯交换。

顺带一提：`generate_sign()` 的参数注释提到了 URL 编码后的字符串，但当前这几条业务请求的实际调用传入的是未编码原文。读项目时要沿着调用点核对，不要只信一条旧注释。

### 第二关，也是重点：保存答案的两套大小写

保存一道题时，当前实现会组织两份结构相近、却不完全相同的数据。

**参与签名的 questions：**

```json
[{"questionid":"q-demo","answerid":"a-demo-1,a-demo-2"}]
```

**真正放进 HTTP 请求体的 questions：**

```json
[{"QuestionID":"q-demo","AnswerID":"a-demo-1,a-demo-2"}]
```

看起来只是大小写，处理时却不能混用。

完整签名原文为一行：

```text
kpid=kp-demo&questions=[{"questionid":"q-demo","answerid":"a-demo-1,a-demo-2"}]
```

对应的请求体形状是：

```json
{
  "kpid": "kp-demo",
  "questions": [
    {"QuestionID": "q-demo", "AnswerID": "a-demo-1,a-demo-2"}
  ],
  "sign": "<由签名原文计算得到的小写十六进制字符串>"
}
```

这里的 `sign` 是占位说明，不是可发送的示例签名。

把关键点摊开看：

| 项目 | 当前实现的规则 |
| --- | --- |
| 原文顶层顺序 | 先 `kpid`，再 `&questions=` |
| 原文题目字段 | 小写 `questionid`、`answerid`，按这个顺序构造 |
| 实际请求体字段 | `QuestionID`、`AnswerID` |
| 签名 JSON | `json.dumps(..., separators=(',', ':'), ensure_ascii=False)` |
| 多选答案 | 用英文逗号连接选项 ID；不是字母串，也不是 JSON ID 数组 |
| 字符编码 | UTF-8 |
| 摘要形式 | 小写十六进制 HMAC-SHA256 |
| 是否包含 sign 自身 | 不包含 |
| 是否包含 token、时间戳、完整 URL | 当前这几条请求的签名原文未包含这些内容 |
| 是否对原文先 URL 编码 | 不做 |

需要特别区分两个容易混淆的“格式”：

- **签名原文里的 JSON**需要复现上述紧凑格式。
- **HTTP 请求体**通过 `api_client.post(..., json=body)` 发送。当前签名不是直接对 HTTP body 的原始字节计算，因此不能简单理解成“整个网络请求体必须和那段紧凑字符串一样”。

另一个容易走偏的办法是对整段 JSON 做 `.lower()`。当前源码是明确构造小写字段名，**没有把 ID 的值一起转小写**。同样，当前实现没有排序答案 ID，也没有自动排序 JSON 字段；不要自行添加“规范化”步骤，再期待签名不变。

这部分讲起来像在抠字眼，但签名恰恰就是一个必须抠字眼的地方。

### 用虚构数据在本地拆一遍

下面只复现“组织两份数据 → 计算签名”，**不联网、不读取账号、不提交答案**。它是讲解示例，不是网页原始 JS，也不是让业务代码绕过现有引擎另写一套请求。

```python
import hashlib
import hmac
import json


def build_demo_request(kpid, question_id, answer_ids):
    answer_id = ",".join(answer_ids)
    for_sign = [{"questionid": question_id, "answerid": answer_id}]
    compact_json = json.dumps(
        for_sign, separators=(",", ":"), ensure_ascii=False
    )
    raw = f"kpid={kpid}&questions={compact_json}"
    sign = hmac.new(
        b"demo-key-not-for-production",
        raw.encode("utf-8"),
        hashlib.sha256,
    ).hexdigest()
    body = {
        "kpid": kpid,
        "questions": [{"QuestionID": question_id, "AnswerID": answer_id}],
        "sign": sign,
    }
    return raw, body


raw, body = build_demo_request(
    "kp-demo", "q-demo", ["a-demo-1", "a-demo-2"]
)
assert raw == (
    'kpid=kp-demo&questions='
    '[{"questionid":"q-demo","answerid":"a-demo-1,a-demo-2"}]'
)
assert set(body["questions"][0]) == {"QuestionID", "AnswerID"}
assert len(body["sign"]) == 64
print(raw)
print(body["sign"])
```

这个例子适合用来理解“为什么空格和大小写会影响结果”。真实维护时还要将原文和摘要与授权浏览器样本逐字节比对，仅检查摘要长度并不能证明协议正确。

### 第三关：保存完答案，还没结束

逐题 `SaveEvaluateAnswer` 之后，当前引擎会调用 `SaveTestMemberInfo` 提交评估信息。

它参与签名的原文是：

```text
kpid=kp-demo&questions=[]
```

请求体则是：

```json
{
  "kpid": "kp-demo",
  "questions": [],
  "sign": "<对应这条原文的签名>"
}
```

这里空数组不是“忘了装答案”。在当前调用流程中，答案已经逐题保存，最后一步使用空数组提交评估信息。我们能确认的是客户端如何调用，不是据此推断服务器内部如何存储答案。

于是，一个知识点的核心步骤应该读成：

```text
开始评估并取得题目
  ↓
每道题：查题库 → 有答案就签名并保存
  ↓
所有题目处理后：用 questions=[] 的原文签名
  ↓
提交评估信息
```

少看最后一步，很容易把“保存过答案”理解成“完成了整个评估”。

## 第四章：签名通了，项目还没做完

终于弄懂签名，当然值得高兴。但它解决的是请求协议中的一部分，不是整个程序的可靠性。

### 答案不是签名算出来的

当前 API 模式从题库按题目 ID 精确匹配，读取标记为 `isTrue` 的选项 ID，再用逗号连接提交。共享实现是 [`find_correct_answer_ids()`](../src/utils/bank_matcher.py)。

```text
本次题目 id
  ↓
题库中查找同 ID 的题目
  ├─ 找不到 / 没有正确选项 → skipped
  └─ 找到正确选项 → 取选项 ID → 签名并保存
```

这里没有让 AI 临场推理答案。前面提到的 AI，是在我整理好签名分析与对比结果后，帮助完成 API 模式的开发，以及后续代码迭代；不要把“开发中用了 AI”误解成“学生评估 API 模式会用 AI 自动答出所有题”。评估出题插件是另外一个功能。

教师端提取也使用另一套认证和接口，沿班级、课程、章节、知识点、题目和选项整理题库。它要求对应教师权限，不能靠学生 token 或一个签名获得。

### HTTP 200 只是第一层

请求发出去、HTTP 成功、业务成功、最终通过，是四件不同的事情。

当前学生评估引擎的判断也不是一个模板套到底：

- 课程详情和未完成章节主要检查 `success` 及 `data`；
- 开始评估检查 `code == 0` 及 `data`；
- 保存答案与提交评估信息接受 `code == 0` 或 `success` 为真。

实际响应中的 JSON 和平台最终状态都要看。发生问题时，不要只凭 Network 里一个绿色的 200 就给流程宣布胜利。

当前代码还会预检查 `isPass` 和 `times`，跳过已通过或次数达到 3 次的知识点；开始评估返回已评估/次数用尽提示时也会跳过。次数由服务端控制，程序不是重置次数的工具。

### 现在也有没收拾完的角落

我更希望文档说明白这些，而不是写成“签名搞定，从此一劳永逸”：

- **缺题会跳过，但不一定停止交卷。** 当前循环处理完后仍可能提交评估信息。
- **保存成功不等于答对。** `success` 计数代表保存调用成功，不是判分结果。
- **已处理知识点数不等于通过数。** 当前统计对交卷失败等情况区分还不够细。
- **停止不是撤回请求。** 当前通常等知识点处理结束再停止，不是点一下立即中断一切。
- **重试不等于零风险。** 网络超时可能发生在服务端已经处理之后，重复 POST 需要谨慎。

具体源码边界和后续改进建议见 [架构文档的已知限制](ARCHITECTURE.md#9-已知限制文档别比程序更乐观)。

## 第五章：从能用的脚本，到现在这个桌面工作台

现在回头看，项目并不是一开始就有清晰的分层、统一的请求客户端和一套插件系统。

早期用浏览器自动化把流程串起来，后来为准确性和稳定性继续折腾 API，弄懂签名之后，又得面对登录状态、题库、后台任务、窗口刷新、浏览器资源和不同功能互相影响的问题。

这些东西不是把一个请求写对就能自动解决的。项目经过多个版本的大更新和架构修改，才慢慢变成现在的样子。

按学习和实现的主线概括，大致是这样；它不是带精确版本号的发布年表：

```text
先让浏览器替我完成页面操作
  ↓
遇到准确性和稳定性问题，开始观察网络请求
  ↓
第一次读 JS 误把 HMAC-SHA256 当作 SHA256，暂时放弃
  ↓
重新搜索完整算法名，理解 key；打断点取得原文并与抓包签名对上
  ↓
整理验证结果交给 AI，实现学生评估的 API 请求流程
  ↓
在多轮更新中调整认证、题库、请求、浏览器与 UI 的分工
  ↓
当前 GUI 工作台：浏览器路径与 API 路径并存，插件扩展功能
```

现在源码中可以看到这些分工：

| 当问题不再只是一道题时 | 当前负责的模块 |
| --- | --- |
| 请求频率、网络失败与重试 | `src/core/api_client.py` |
| 多种登录会话与浏览器线程归属 | `src/core/browser.py`、`_worker_engine.py` |
| 学生登录、课程请求、页面操作拆开维护 | `src/auth/_student_*`，由 `student.py` 保持兼容导出 |
| 题库导入、课程校验与预览 | `src/extraction/bank_service.py` |
| 多个 API 业务共用答案 ID 匹配 | `src/utils/bank_matcher.py` |
| 进度与日志回到界面显示 | `AnswerProgressDialog`、`run_background_task` |
| 扩展功能有自己的入口 | `plugins/`、`PluginManager`、`PluginContext` |

API 模式让一部分业务不再依赖逐题点页面，但没有消灭所有问题。浏览器仍然负责登录和兼容路径；接口规则变化，也一样需要维护。

对我来说，这个过程更像边走边补地图。不是先成为很厉害的程序员，再开始做项目；是遇到自己不会的问题，借助工具一点点理解，项目和自己的认识一起往前走。

## 第六章：如果以后又不能用了，从哪里查？

不要一上来就换 key，也不要直接提高重试次数。先确定变的是哪一层。

| 现象 | 优先核对 |
| --- | --- |
| 未登录、身份无效、权限不足 | token 是否过期/被撤销、账号角色与课程权限 |
| HTTP 成功但业务拒绝 | JSON 的 `code` / `success` / `msg`，不要只看状态码 |
| 签名相关拒绝 | 原文顺序、字段大小写、空格、编码、算法和 key 的当前来源 |
| 请求返回题目但题库匹配不到 | 题目 ID、课程、题库版本、正确选项标记 |
| 单题保存成功但课程状态未完成 | 是否执行最终提交、提交响应、实际平台状态 |
| 页面模式失败，API 模式没异常 | DOM、选择器、等待条件与页面反馈 |
| 请求很慢 | 配置档位、重试退避、业务层额外等待，不只是网络速度 |
| 停止按钮没有立刻结束 | 当前知识点是否仍在处理，是否已有在途请求 |

重新分析签名时，最好留一份**脱敏的本地对照表**：

```text
接口动作：保存一道题
网页送入签名函数的原文：……
Python 生成的原文：……
字段顺序 / 大小写 / 空格 / 编码差异：……
算法与 key 来源：……
网页计算结果与本地结果是否一致：……
HTTP 状态与业务响应：……
```

先比输入，再比输出。输入不同的时候，盯着两个摘要发呆没有什么用。

还有一个很重要的小事：HAR、Copy as cURL、请求头截图和应用日志都可能带 token、Cookie、账号或业务数据。给 AI 分析或发 Issue 之前先脱敏。当前引擎会记录部分签名原文和请求体，所以“这是程序自己打的日志”也不意味着可以直接公开。

## 后记：不是很会，但还是一点点弄明白了

我本身算技术小白，编程能力也很基础。这个项目里不少东西，都是先遇到问题，再去查，再借助 AI 分析，最后试着把它接回自己的代码里。

所以这篇最想留下的，并不是一段签名函数。函数会变，接口会变，网页也会更新。

更值得留下的是这条思路：**先观察正常页面怎么做，再找到负责这件事的 JS，把输入、处理和输出一点点对上。算法名字别只看认识的半截，不懂的 key 也别当成没用；自己验证清楚，再把结果交给 AI 协助实现。**

从浏览器里一次不太稳定的点击，到今天这一堆模块，确实绕了不少路。现在也谈不上完美，但至少有些以前只觉得“很玄”的东西，终于能说清楚它为什么这样工作了。

如果你也是基础有限、对着代码不知道从哪儿下手，希望这篇能让你少一点“是不是只有我看不懂”的感觉。

看不懂可以慢慢拆。这个项目本来就是这样一点点长出来的。
